## idx 34 — Quasipolynomial Simulation of DNNF by a Non-determinstic Read-Once Branching Program (Igor Razgon, Department of Computer Science and Information Systems, Birkbeck, University of London, igor@dcs.bbk.ac.uk, marked B; source lines 10,418-10,589, paper pp. 367-375, TOC paper 26, DOI 10.1007/978-3-319-23219-5 26; title-page spelling as extracted `Non-determinstic`, the volume TOC spells `Non-deterministic`; first-page footnote line 10,434 `-c Springer International Publishing Switzerland 2015`)

Abstract verbatim: "We prove that dnnfs can be simulated by Non-deterministic Read-Once Branching Programs (nrobps) of quasi-polynomial size. As a result, all the exponential lower bounds for nrobps immediately apply for dnnfs."
Introduction (verbatim facts): Decomposable Negation Normal Forms (dnnfs) [3] are a well-known formalism in propositional knowledge compilation, notable for efficient representation of cnfs with bounded structural parameters; the dnnf lower bounds are much less understood — it has been shown only recently that dnnfs can be exponentially large on (monotone 2-)cnfs [2]; prior to that, on monotone functions dnnfs are not better than monotone dnnfs [6], so all lower bounds for monotone circuits apply for dnnfs; using monotone circuits to obtain new dnnf lower bounds is hardly appropriate because, in light of [2], on monotone functions dnnfs are much weaker than monotone circuits. This paper shows dnnfs are strongly related to Non-deterministic Read-Once Branching Programs (nrobps), thought of as Free Binary Decision Diagrams (fbdds) with or-nodes; a dnnf can be transformed into a nrobp with a quasi-polynomial increase of size, so all exponential lower bounds known for nrobps (see e.g. [5,8]) apply for dnnfs; nrobps can be linearly simulated by dnnfs (using a modification of the simulation of fbdds by dnnfs proposed in [4]), so the result makes significant progress in understanding dnnf complexity — instead of establishing exponential lower bounds directly for dnnfs, one can do this for nrobps, much better understood from the lower-bound perspective. The simulation adapts to unrestricted dnnfs the approach used in [1] for quasi-polynomial simulation of decision dnnfs by fbdds, representing nrobps in a form where variables carry no labels and edges are labelled with literals; each input node u of the dnnf is represented as an edge labelled with the literal of u, and these are the only labelled edges (compare [1] where the labelling is "pertained" to or nodes, impossible for unrestricted dnnfs where the or nodes can have arbitrary structure).

## idx 37 — MiniSearch: A Solver-Independent Meta-Search Language for MiniZinc (source lines 10,590-10,781; Andrea Rendl (TU Wien), Tias Guns, Peter J. Stuckey (NICTA/University of Melbourne), Guido Tack; the paper abstract and sections are fully consumed — the notes file is the authoritative copy; paper pp. 376-393, TOC paper 27)
- Abstract verbatim: much of the power of CP comes from the ability to create complex hybrid search algorithms specific to an application; unfortunately there is no widely accepted standard for specifying search, and each solver typically requires detailed knowledge to build complex searches, making the barrier to entry for exploring different search methods quite high; search is a core part of the solver and usually highly optimised, so imposing on the solver writer to change this part of their system is significant. The paper investigates how powerful a uniform language for meta-search can be without placing any burden on the solver writer; the key is to interact with the solver only when a solution is found; MiniSearch is a meta-search language that can directly use any FlatZinc solver, optionally interacting with solvers through an efficient C++ API; expressiveness and performance are illustrated using different solvers on a number of examples.
- Introduction (verbatim facts): meta-search such as Branch-and-Bound (BaB) or Large Neighbourhood Search (LNS) happens on top of CP tree search and aids finding good solutions, often by encoding meta-information a modeller has about the problem; there is no widely accepted standard for controlling search or meta-search; high-level languages are similar in how constraints are specified but differ significantly in how search can be specified, from built-in minimisation/maximisation only to fully programmable search; the main trade-off is expressivity versus required integration with the underlying solver; fully programmable search including meta-search is most expressive but requires deep knowledge of and tight integration with a specific solver; OPL [24] and COMET [13] provide convenient abstractions for programmable search for the solvers bundled with these languages; solver-independent languages Esira [3], Essence [5] and Essence′ [6] do not support search specifications; Zinc [12] and MiniZinc [16] support specifying variable and value ordering heuristics to CP solvers but no real control over the search. Search combinators [19] was recently proposed as a generic meta-search language for CP solvers, interacting with the solver at every node in the search tree; while very expressive, it requires significant engineering effort to implement for existing solvers, since the solvers' search engines are highly optimised and tightly integrated with the propagation engine and state-space maintenance. MiniSearch has three design objectives: a minimal solver interface to facilitate solver support, expressiveness, and most importantly solver-independence. The minimal interface stems from lessons learnt in search combinators' per-node interaction; MiniSearch interacts with the underlying solving system only at every solution, at which constraints can be added or constraints in a well-defined scope removed before asking for the next solution, and if the underlying solver does not support dynamic adding/removing of constraints MiniSearch can emulate this for little overhead. Despite the lightweight interface MiniSearch supports BaB, lexicographic BaB, LNS variants, AND/OR search, diverse solution search, and more, and interactive optimisation applications; since MiniSearch builds on MiniZinc, all MiniZinc language features and built-ins can be used, for instance to formulate custom neighbourhoods. All solvers that can read and solve FlatZinc, which the majority of CP solvers do [15,22], can be used with MiniSearch; solvers providing native meta-search variants such as branch-and-bound can declare so and avoid executing the MiniSearch decomposition, at the language level similar to MiniZinc's handling of global constraints, so solvers can apply their strengths during meta-search despite the minimal interface.
- Section 2 The MiniSearch language: MiniSearch is a high-level meta-search language based on MiniZinc 2.0 [23], used for formulating the model and the constraints posted during search, with language extensions for specifying the search; a MiniSearch specification is provided, together with the `search` keyword, as an argument to MiniZinc's `solve` item, executed by the MiniSearch kernel (Sec. 4). Built-in extensions (Table 1, caption `Table 1. MiniSearch built-ins`): `next()` find the next solution; `post(c)` post the MiniZinc constraint c in the current scope; `scope(s)` open a local scope containing search s; `s1 /\ s2` run s1 and iff successful, run s2; `s1 \/ s2` run s1 and iff it fails, run s2; `if s then s1 else s2` if s is successful run s1 otherwise s2; `repeat(s)` repeat search s until break is executed; `repeat (i in 1..N)(s)` repeat s N times or until break; `break()` break within a repeat; `fail()` return "failure"; `skip()` return "success"; `time_limit(ms,s)` run s until timelimit ms is reached; `print(S)` print MiniZinc output string S; `print()` print solution according to model output specification; `c := v` assign parameter c the value v; `commit()` commit to last found solution in function scope; `sol(v)` return solution value of variable v; `hasSol()` returns true if a solution has been found. Users can define functions such as branch-and-bound minimisation: `include "minisearch.mzn"; var int: obj; solve search minimize_bab(obj); output ["Objective: "+show(obj)]` with `function ann: minimize_bab(var int: obj) = …`.
- Adding constraints and variables: a constraint is added by calling `post()` with a constraint as argument; constraints can be formulated using the same MiniZinc constructs as in the model, including global constraints, user-defined functions and predicates; variables can be dynamically added during search using the MiniZinc `let` construct (see AND/OR search in Sec. 3.3). Search scopes define the lifespan of constraints and variables in the model; MiniSearch has an implicit global search scope containing all variables and constraints of the model; a new search scope is created with `scope(s)` taking a MiniSearch specification s; when entering a scope, search is assumed to start from the root again; whenever the execution leaves a scope, all constraints and variables added in the scope are removed from the model and the solver, and execution in the enclosing scope resumes from the point where it left off.
- Section 2.2 MiniSearch control built-ins: all MiniSearch built-ins have an implicit return value representing "success" (true) or "failure" (false), and all built-ins execute their arguments in order. The `/\` built-in runs its arguments in order and stops to return false as soon as one of its arguments fails; the `\/` built-in stops and returns success as soon as one of its arguments succeeds; existing MiniZinc control mechanisms such as `if then else endif` expressions can be used as well; `repeat(s)` takes a MiniSearch specification s and repeats it until a `break` built-in is executed, returning false if a break happened, otherwise returning what s returned; the delimited variant `repeat(i in 1..N)(s)` executes s for N iterations (or until break is executed). `time_limit(ms,s)` imposes a time limit ms (in milliseconds) on any MiniSearch specification s, so s stops whenever the time limit is reached, returning its current status; time-limits are handled transparently by the MiniSearch kernel as an exception. Standard MiniZinc constant parameters such as `int: N=10;` cannot change their value, so the assignment operator `:=` was added, usable only inside a MiniSearch specification, overwriting the constant's current value with the supplied value.
- Section 2.3 Solution management: the strength of a meta-search language lies in using intermediate solutions to guide the remaining search (branch-and-bound needs to access the objective to post further constraints, LNS thaws some of the variables in a solution to continue in that neighbourhood); the most recently found solution is always accessible using `sol`, where `sol(x)` returns the value of x in the last solution, and `hasSol()` tests whether a solution exists. When a MiniSearch strategy is defined as a MiniZinc function, a local solution scope is created, so any solution found by a call to `next()` inside the function is visible for the code in the function body, but not for the caller of the function when the function returns, allowing calls to `next()` to be encapsulated (a function can make "tentative" calls to next in a nested search scope and only commit if these succeed — Sec. 3.3 shows AND/OR search on this principle); to make the current solution accessible to the caller the function must call `commit()`; a function returns "success" if it called `commit()` at least once, and "failure" otherwise, and the last solution committed by the function becomes the current solution of the caller. `print()` without arguments prints the last found solution in the format specified in the model's `output` item; `print(s)` gives more fine-grained control over the output, the string constructed dynamically from values in the solution using calls to `sol`; MiniSearch can be debugged using `print()` and MiniZinc's `trace()` function to display values of parameters, variables, and arbitrary expressions during search; the MiniSearch interpreter uses the C++ stack, so C++ debuggers can be used to follow the meta-search.
- Section 2.4 A Library of Search Strategies: the most common meta-search approaches are defined and collected in the standard library `minisearch.mzn`, usable within any MiniZinc model that includes the library.
- Section 3 MiniSearch examples: despite MiniSearch's limited communication with the solver it provides enough power to implement many useful complex searches. Section 3.1 Lexicographic BaB: in multi-objective optimisation, lexicographic optimisation can be used if the objectives can be ranked according to their importance, minimising (or maximising) an array of objectives lexicographically; lexicographic optimisation can be more efficient than the commonly used approach of obtaining a single objective term by multiplying the components of the lexicographic objective with different constants, as the latter leads to large objective values, and potentially overflow; analogous to branch-and-bound, the global constraint `lex_less` is posted so that the next solution is lexicographically smaller than the previous one; `function ann: minimize_lex(array[int] of var int: objs) = next() /\ commit() /\ print() /\ …`.
- Section 3.1 Lexicographic BaB code verbatim: `repeat( scope( post(lex_less(objs, [sol(objs[i]) | i in index_set(objs)])) /\ if next() then commit() /\ print() else break endif ) )` — the paper explains: line 2 searches for an initial solution and, if successful, repeatedly opens a new scope (line 3), posts the lexicographic constraint (line 4), searches for another solution (line 5), so in each iteration of repeat one lex constraint is added and all previously added lex constraints are removed due to the scope; this is not required but beneficial, since posting several lex-constraints can cause overhead if many intermediate solutions are found. Section 3.2 Large Neighbourhood Search (LNS): large area neighbourhood search [20] is an essential method in the toolkit of CP practitioners, allowing CP solvers to find very good solutions to very large problems by iteratively searching large neighbourhoods (close) to optimality; **Randomised LNS** explores a random neighbourhood of a given size, surprisingly effective in practice as long as the neighbourhood size is chosen correctly; cumulative scheduling is an example of a successful application [7]. The MiniSearch specification of randomised LNS takes the objective variable, an array of decision variables searched on, the number of iterations, the destruction rate (the size of the neighbourhood) and a time limit for exploring each neighbourhood, with two scopes: in the global scope BaB-style constraints are posted (line 10), in the sub-scope (line 5) the neighbourhoods are searched; the predicate `uniformNeighbourhood` defines the neighbourhood, for each search variable deciding randomly whether to set it to its solution value of the previous solution (line 15): `function ann: lns(var int: obj, array[int] of var int: vars, int: iterations, float: destrRate, int: exploreTime) = repeat (i in 1..iterations) (print("Iteration "+show(i)+"\n") /\ scope(post(uniformNeighbourhood(vars,destrRate)) /\ time_limit(exploreTime, minimize_bab(obj)) /\ commit() /\ print()) /\ post(obj < sol(obj)))`, `predicate uniformNeighbourhood(array[int] of var int: x, float: destrRate) = if hasSol() then forall(i in index_set(x)) (if uniform(0.0,1.0) > destrRate then x[i] = sol(x[i]) else true endif) else true endif`. **Adaptive LNS** modifies the neighbourhood size over the course of the iterations depending on the success of previous iterations; a simple variant where the neighbourhood size parameter `nSize` (line 3) is step-wise enlarged each time no solution is found (line 9), the `fail` command failing the current conjunction and hence avoiding that the `post` command on line 10 is executed: `function ann: adaptive_lns(var int: obj, array[int] of var int: vars, int: iterations, int: initRate, int: exploreTime) = let {int: nSize = initRate, int: step = 1;} in repeat (i in 1..iterations) (print("Iteration "+show(i)+", rate="+show(nSize)+"\n") /\ scope((post(uniformNeighbourhood(vars,nSize/100.0)) /\ time_limit(exploreTime, minimize_bab(obj)) /\ commit() /\ print()) \/ (nSize := nSize + step /\ fail)) /\ post(obj < sol(obj)))`. **Custom Neighbourhoods** can be effective if they capture insight into the problem structure; in a Vehicle Routing Problem (VRP) one may want to keep certain vehicle tours or vehicle-customer assignments; the paper shows a custom neighbourhood easily specified in MiniSearch — the predicate `keepTour` (line 1) posts the tour constraints of a given vehicle number `vNum`, if a solution exists the neighbourhood predicate (line 4) determines the number of customers of each vehicle (line 7) and then randomly chooses to keep the vehicle's tour (line 8), a high customer usage resulting in a higher chance of keeping the vehicle; the predicate can be used instead of the uniform neighbourhood in the LNS specifications above: `predicate keepTour(int: vNum) = forall (i in 1..nbCustomers where sol(vehicle[i]) == vNum) (successor[i] = sol(successor[i]))`, `predicate vehicleNeighbourhood() = if hasSol() then forall (v in 1..nbVehicles) (let {int: usage = sum(c in 1..nbCustomers) (sol(vehicle[c]) == v)} in if usage > uniform(0,nbCustomers) then …`.
- Section 6 Related Work (companion-comparison facts, as recorded in pass 1 of this notes file): the starting point for MiniSearch is search combinators [19], and MiniSearch is indeed a combinator language; the MiniSearch language is more restricted than search combinators, which can interact with the search at every node of the tree, essentially replacing the solver's built-in search, while MiniSearch only interacts with the solver's search at the granularity of solutions; examples not possible in MiniSearch are the use of average depth of failure, custom limits based on how many search nodes with a particular property have been encountered, and heuristics such as limited discrepancy search [8] and iterative deepening; other search-combinator expressions are expressible with MiniSearch, as witnessed by the library of strategies in the paper. Neither search combinators nor MiniSearch support fully programmable search, especially variable and value ordering heuristics, which interact with the internal data structures of the solver; these strategies are important but cannot be implemented without deep hooks into the solver. Objective CP [26] can express complex meta-search at the model level, executed by any Objective CP solver, e.g. a CP-style search can be implemented using a MIP solver, so it also provides solver-independent search, but through a much more fine-grained interface supporting interaction at each search node; the fine-grained interface means adding a new solver to Objective CP is complex, in particular supporting the reverse mapping of information from solver objects to model objects. Possibly the closest system to MiniSearch is OPL Script [25], a scripting language for combining models, which also communicates to solvers via models and solutions; distinct from MiniSearch it is object-oriented and provides models as first-class objects, supporting construction and modification of multiple models, and it can communicate more information than just variables and constraints, including dual values, bases, and various statistics, but the language is tightly linked to the CP/MIP solver ILOG CPLEX CP Optimizer, whereas MiniSearch can use any FlatZinc solver. AMPL Script [4] is similar in many respects to OPL script, a more basic scripting language not supporting function definitions; it has no concept of scopes, supporting instead adding, dropping and restoring variables and constraints from the model dynamically; it interacts with the solver through requests to solve, continuing until a termination condition arises (optimality proven or timeout), so its natural interaction level is more like `minimize_bab()` than `next()`.
